# Modularity and selectable components

The pipeline is **embedding → sampled fields → physical assembly → controller →
integration/contact → observations, rewards, losses, and gradients**. Most of
these stages are replaceable, but their choices do not form an unrestricted
Cartesian product. A new physics family can reuse a decoder and controller only
when dimensions, channels, sampled fields, state contracts, and numerical settings
match. It generally requires different assembly and compilation.

This is a selector map of the current code, complementary to the
[architecture guide](COMPONENTS_AND_GYMNASIUM.md) and
[support/validation matrix](CAPABILITIES.md). It distinguishes three interfaces:

| Interface | What the caller supplies | Scope of customization |
| --- | --- | --- |
| **JAX engine**: `engine.make`, `make_vec`, pure rollout builders | Decoder embedding dictionary plus `SpringConfig` or `BodyConfig` | Decoder, assembly settings, physics, solvers, differentiable policies and losses |
| **Native Warp engine**: the same factories with `backend="warp"`; `Episode` / `SolidEpisode` | Resolved `Bundle` / `SolidBundle` arrays; native configuration | Physics, supported solver options, native policy/loss kernels, resolved-array adjoints; `EmbodimentEpisode` adds the decoder/assembly pullback |
| **Registered Gym task**: `codesign_gym.make_vec("SoftWalker…")` | Flat per-cell embodiment vector and bounded actions | Device, precision, driver/preset, lane count, action holding, execution scheduling, rendering, and capacity padding; general engine solver/decoder/controller selectors are **not** factory keywords |

`engine.make` defaults to JAX; registered SoftWalker tasks default to Warp. The
registered wrappers expose NumPy interaction rather than a differentiable
`step` function. Their shared resolved observation/reward layout differs from
the general JAX engine layout.

Controller interface restrictions apply to code running **inside a compiled
simulation episode**: JAX accepts JAX policy functions, while native Warp accepts
Warp policy kernels over its state/parameter/carry buffers. Both support feedback
and recurrence, but there is no automatic translation of an arbitrary JAX neural
network into a Warp kernel. An **external policy driving Gym** can use any
framework and supply ordinary actions.

The Gym gradient boundary means that stateful `env.step(action)` returns NumPy
observations/rewards without exposing their derivatives with respect to actions
or body parameters. Wrapping that call in `jax.grad` is unsupported. Use pure
JAX rollouts or native episode adjoints for differentiable simulation, and the
embodiment bridge for native gradients through decoder/assembly parameters.
Ordinary Gym-based RL such as PPO does not require those simulator derivatives.

Status terms follow [CAPABILITIES.md](CAPABILITIES.md): **supported within stated
constraints**, **experimental or partial**, **not implemented**, and **validation
not established for the specific combination**. The rows below describe supported
selectors unless another status is stated. Source/test links establish the
implementation and concrete coverage, not universal accuracy or performance.
This document adds no new numerical validation claim; release validation is
recorded separately.

## Combinations that are unavailable or restricted

All five existing physics families have JAX and Warp implementations. The
restrictions below concern particular combinations or interfaces, not a missing
Warp or JAX implementation of an entire listed family.

| Requested combination | Current boundary / supported alternative |
| --- | --- |
| 3D springs, or 2D beams/FEM | Not implemented. Choose spring 2D, beam/Hex FEM 3D, or MPM 2D/3D. |
| Active stress with spring, beam or FEM | Unsupported; active stress is MPM-only. Those other families use active strain. |
| Kvaerno3 with beam, FEM or MPM | Unsupported. Kvaerno3 is spring-only; all five families support backward Euler. |
| Diffrax Kvaerno3 with GMRES, or JAX-native Kvaerno3 with dense solves | Unsupported pairings. The Diffrax spring path requires dense solves; the JAX-native spring path requires GMRES. Warp uses its own native spring stages. |
| Native Warp exports with adaptive timestep halving | Unsupported: export requires fixed steps. MPM embodiment export also requires right preconditioning. |
| JAX solver names/options used unchanged in Warp | Not interchangeable. Native solids require adaptive dynamic Krylov and cached tangents; beam tangents require autodiff. MPM node-block/compact-grid options do not apply to native solids. |
| Independent spatial Poisson mechanics in the spring model | Not available; the shared field exists, but the spring law has no independent continuum Poisson response. |
| General self-contact, hard contact, imported heightfields or arbitrary collision meshes | Not implemented. Current contact uses regularized terrain planes and rounded boxes/compositions. |
| Changing dimension/topology during a traced or captured step; ordinary gradients of hard occupancy/channel labels | Unsupported. Reconstruct/reset for discrete changes and differentiate eligible continuous parameters with fixed discrete structure. |
| Arbitrary JAX/Python policy or loss callable inside a native Warp graph | Not accepted directly. Supply native Warp policy/objective kernels; recurrent feedback itself is supported. |
| Native physics/embodiment bridge called as an ordinary `jax.jit` simulation callback | Unsupported. `EmbodimentEpisode` provides the explicit decoder/assembly pullback at a host episode boundary. |
| Gradients through registered Gym `step` or its body assembly | Not implemented. Use the differentiable engine rollout or native episode/embodiment interfaces. |
| Arbitrary decoder/solver/controller keywords on registered Gym factories | Not exposed there. Registered presets fix these internals; use the engine or extend a builder for deeper configuration. The common `integrator` keyword exposes only backward Euler and spring native Kvaerno; it rejects legacy Diffrax Kvaerno. |
| Native Warp `execution="parallel"` on CPU | Unsupported. Native CPU uses serial reference execution; parallel native lanes require CUDA. |
| Arbitrary checkpoint resume after switching backend, topology, objective or parameter schema | Unsupported. Portable body conversion is separate from compatible optimizer/runtime continuation. |
| Optimizing every programmable field with the supplied implicit co-optimization command | Not exposed: that workflow freezes density, discrete routing and hidden network structure. Other engine workflows may differentiate eligible continuous fields. |

Some gaps are **validation limits**, rather than an unavailable combination:

- Terrain-parameter optimization has no established public workflow coverage;
  native adjoints omit terrain fields, while normal JAX rollout builders bind
  the terrain. Terrain contact support does not imply terrain gradients.
- Explicit MPM is experimental diagnostic code, not a production environment
  selector.
- Tests do not cover every decoder × controller × terrain × solver × body size ×
  precision/device combination, or arbitrary long large-deformation trajectories.
- Headless rendering checks do not certify interactive Newton playback on every
  graphics setup. Particle/element inspection also requires those data to exist
  in the recording.

## Choosing compatible combinations

For direct Gym use, choose the registered physics/terrain preset first, then
`backend`, `device`, `dtype`, `integrator`, `num_envs`, and `physics_steps_per_action`. Supply
the registered per-cell embodiment vector and external actions. The available
IDs are `SoftWalkerSpring2D`, `SoftWalkerBeam3D`, `SoftWalkerHexFEM3D`,
`SoftWalkerMPM2D`, and `SoftWalkerMPM3D`, each also with `-Stairs` / `-Gaps`.

For differentiable body/controller experiments, choose a decoder and compatible
physics configuration, validate the sampled/assembled body, and bind a pure JAX
rollout or native episode/embodiment bridge. Select the loss and optimizer at
that boundary. Preserve fixed discrete structure for differentiation, and check
forward/adjoint status for the actual rollout.

The main exclusions are arbitrary topology changes inside a simulation,
general self-contact, arbitrary mesh/heightfield collision input, gradients
through the NumPy Gym API, and unrestricted interchange of JAX callables with
Warp kernels. Terrain parameter optimization and untested cross-products remain
explicitly unqualified. Refer to [CAPABILITIES.md](CAPABILITIES.md) for the
specific evidence and remaining restrictions rather than treating this selector
inventory as certification.
