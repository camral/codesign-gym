# Gradient accuracy and repeatable CUDA execution

Three separate issues were isolated using the frozen follow-up cases. The
repairs keep the forward equations and gradient comparison thresholds intact.

## Positive actuator work

Positive work remains `max(work, 0)`. At exactly zero, its derivative is not
unique. JAX assigns a half derivative, while Warp's ordinary `max` assigns zero
to the work argument in this expression. Native spring, beam, FEM and MPM work
kernels now use a shared custom derivative with slopes 0, 0.5 and 1 for negative,
zero and positive work. The forward values, including signed zero, are unchanged.
This matters for zero actuator states during settling and zero actuator routing.

## Native adjoint accuracy

`SolidConfig.adjoint_rtol64` defaults to `2e-11`; `adjoint_rtol32` defaults to
`2e-5`. A transpose solve uses the smaller of this target and the configured
forward linear tolerance. This changes the Krylov stopping target during graph
construction, with the same workspace and iteration budget. Forward Newton
settings and the independent residual failure checks are unchanged. Old saved
bundles load with these defaults; the fields are included in new serialized
configurations.

The full 1,400-step float64 spring case exposed small displacement gradients
formed by cancellation. A tighter transpose target resolved their discrepancy
against a separate dense CPU reference without changing the forward trajectory.

For float32 MPM, the existing `linear_refinements` budget now targets
`min(linear_limit, 4 * float32_epsilon)` on transpose solves. Each correction is
accepted only if its independently measured residual improves. Forward solves,
float64 MPM, solid refinement targets and failure thresholds are unchanged.
`linear_refinements=0` still disables refinement. The failing changed-command
volume-gradient cases use a nonzero budget and now pass their original 0.3%
norm threshold against both the baseline path and promoted float64 inputs.

## Deterministic JAX GPU reductions

CUDA scatter additions can accumulate in different orders, including scatter
operations generated by differentiation of gathers. This produced small repeat
differences in the full spring gradient even though each result agreed with
the independent dense reference.

For strict repeat certification, select:

```python
from envs.soft_walker.engine.execution import ResidentPolicy

policy = ResidentPolicy("cuda", deterministic_reductions=True)
```

The resident locomotion and scenario CLIs expose the same choice as
`--deterministic-reductions`. It enables deterministic GPU lowering together
with XLA's optimized scatter determinism expander, per executable. CPU compiler
options remain unchanged. Existing residency, finite-value and repeat checks
remain mandatory; this setting does not bypass certification.

This option affects deterministic GPU lowering beyond springs and can cost
runtime. It remains off by default. On the repaired full spring diagnostic,
repeated gradients were bitwise identical and the whole-GPU audit passed. The
unoptimized deterministic scatter lowering was much slower and is not exposed
as the production setting.

The mass/velocity parameter-adjoint test also now compares the entire final
state and loss at a dtype-scaled roundoff allowance instead of demanding exact
equality between separate atomic reductions. Its gradient limits are unchanged.
